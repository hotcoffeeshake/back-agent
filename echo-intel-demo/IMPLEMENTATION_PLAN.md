## 2. 问题一：场景可以复用吗？10 条数据是否必须 Mock？

### 2.1 场景：可以复用，且文档「闭环 1」就是场景的准确定义

文档第 5.2 节原文（闭环 1）：

> 客户进线 → 身份与记忆解析 → 需求澄清 → 证据检索与实时方案校验 → Journey Leader 校验并输出多商户可执行方案；在客户确认前止于方案。

本 Demo 的「售前方案推荐闭环」与此**逐字对应**：身份与记忆 → 需求诊断（需求澄清）→ 方案生成（证据检索 + 实时方案校验）→ Customer Journey Leader 汇总输出可执行方案，**止于方案、不进入支付锁档**（对应「在客户确认前止于方案」）。无分叉。

### 2.2 Mock 数据：「必须 Mock」是文档要求，「10 条」不是文档规定

- **必须 Mock（文档原文要求）**：
  - 第 8.3 节：「所有工具与 Webhook 具有确定性 Mock，支持超时、冲突、限流、部分失败和乱序注入，供离线回放和 CI 使用。」
  - 第 17 章：「每项生产能力保持本地 Mock，支持离线回放与故障测试。」
  - 附录 D：「所有 MCP/适配器具有 Schema、超时、重试、幂等、错误码、Scope、审计和 Mock。」
  - **结论：工具数据必须通过 Mock 提供，这是文档的硬性要求。**

- **「10 条」不是文档规定（Demo 层约定）**：
  - 文档未规定测试集条数。文档的评测资产口径是「2,000 条黄金集、BadCase、安全集、工具模拟」（第 12.3 节），这是**完整生产**目标，非最小 Demo。
  - 「10 条（8 可执行 + 2 不可执行）」是为验证「可执行方案率 ≥80%」（表格 46）而设的**最小测试集**，属于 Demo 层实现选择，**可增可减，不影响对齐**。
  - 其语义对齐文档第 12.3 节「工具模拟」与第 8.3 节「离线回放」——用一批确定性样例回放验证成功率。

## 3. 问题二：文档「Mock 工具网关」是否已有说明？

**结论：文档没有独立的「Mock 工具网关」章节，但 Mock 作为「工具/MCP/适配器」的通用属性，已在以下 6 处说明。本方案不自创「Mock 工具网关」新概念，直接引用以下章节，不重复改写。**

| # | 章节 | 原文要点 |
|---|---|---|
| 1 | 第 8.3 节「外部 API 与事件」 | 所有工具与 Webhook 具有确定性 Mock，支持超时、冲突、限流、部分失败和乱序注入，供离线回放和 CI 使用 |
| 2 | 第 17 章「从当前仓库演进」 | 当前 MVP 不应推倒重写；每项生产能力保持本地 Mock，支持离线回放与故障测试 |
| 3 | 表格 225「当前资产」 | 「Mock MCP」→ 保留「工具名、Schema、错误码、幂等约定」→ 重构为「实现 SAE MCP Gateway 和真实业务适配器」 |
| 4 | 附录 A 表格 238「契约项」 | Mock：确定性样例、超时/冲突/失败注入、黄金数据 |
| 5 | 第 16.3 节「最终交付物」 | MCP Mock 与业务适配器 |
| 6 | 附录 D「上线检查表」 | 所有 MCP/适配器具有 Schema、超时、重试、幂等、错误码、Scope、审计和 Mock |

**据此对齐的落地结论：**

1. **不新建「Mock 工具网关」章节**。本 Demo 的 mock 工具属于文档表格 225 的「Mock MCP」演进范畴，其能力边界按第 8.1 节「MCP/适配器层」+ 表格 65（组件：商品、库存/档期、报价、锁档/草稿单、订单/支付/物流、接管、审批、知识工具）+ 表格 129（L0–L3 风险分级）界定。
2. **工具名按文档锁定的口径命名**（表格 225「保留工具名」无清单，文档未锁定具体函数名）。经排查，V1.0/V2.0 及所有源文件均无具体 Mock 工具名清单，且「当前仓库」MVP 源码不在本机。**结论**：工具按文档锁定的「表格 65 适配器层组件 + 表格 129 L0 只读」组织，函数名属 Demo 层实现。已按此重命名（见第 5 节）。

## 7. 可观测与审计层（Demo 层约定 · 弥合方案蓝图断层）

> **Demo 层约定**：本节为初赛阶段为满足「可追溯 / 可审计」要求而引入的工程约定，并非文档 V2.0 原文步骤，单独标注以与文档区分。

### 7.1 断层说明
- 初赛方案蓝图（`Agent Infra初赛方案PPT框架解读大纲.md`）**明确 6 处**将「**阿里云 AgentLoop**」指定为可观测与审计层，且嵌入阿里云技术栈（Nacos / K8s / 百炼 / 通义），与文档第 8.1 节「适配器层」、附录 D「审计」口径一致。
- 但本 IMPLEMENTATION_PLAN 此前**未引用 AgentLoop**（仅附录 D 泛引「审计」）。该断层是初赛运行期「房间被当作 stdout / 审计通道」导致消息膨胀（闭环 1 单场景 804 条房间消息）与密钥泄露（见 `BUG-credential-leak.md`）的**根因之一**——房间承载了本应由审计层承担的职责。

### 7.2 目标架构（复赛 V0.5 接入）
- 可观测/审计层 = **阿里云 AgentLoop（Agent 可观测与持续优化平台）**：无侵入全链路采集 Trace/Log/Metrics → Trajectory；行为审计 + 异常检测 + 敏感数据访问预警；评估与实验（Agent-as-a-Judge + 数据集回测，自动测 `feasible_rate`）；FinOps（每 agent/工具 Token、耗时归因）；自进化（经验库/记忆库回灌）。
- **兼容性已确认**：AgentLoop 官方兼容列表含 **HiClaw + AgentScope**（本 Demo 的 hiclaw + copaw 即基于此），零改造接入为真。
- 详细能力映射与分阶段落地见 `AGENTLOOP-ALIGNMENT.md`。

### 7.3 初赛兜底（本地审计 + 审计/协同分离）
在复赛接入 AgentLoop 前，初赛以**本地审计**满足可追溯/可审计要求，并已落地「审计层 / 协同层分离」原则：

1. **配置层分离（已落地）**：5 个 agent 的 copaw `config.json` 已置 `show_tool_details:false` + `channels.matrix.filter_tool_messages:true`，工具调用/结果/文件同步输出不再渲染进 Matrix 房间，仅留本地 `copaw.log` 审计；同步启用 `security.file_guard`（拦截读取凭据文件）+ 各 agent `AGENTS.md` 追加「消息经济性政策」。
2. **产物层证据（已落地）**：闭环 1 跑通后产物归集于 `proof-flow1-loop/`（全量房间消息流、各 agent `result.md`/`spec.md`、审计日志，均已脱敏），含 `README.md` 与 `flow-summary.json` 量化摘要（req_01 闭环：3/3 节点验收通过，可执行方案率 2/2=100%）。
3. **遗留 caveat（已记录）**：`mock` 工具网关运行期不可达时方案率为本地降级估算，非真实校验；AgentLoop 接入后可对每次 run 自动回归 `feasible_rate`。
